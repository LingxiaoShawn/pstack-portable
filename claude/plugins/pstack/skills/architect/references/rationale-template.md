# Design rationale

Use the sections needed to explain the decision. Small designs can be a few
paragraphs with a caller example; this template does not require a new file.

## Problem and constraints

The outcome, current code evidence, acceptance criteria and compatibility or
ownership constraints that make the choice non-obvious.

## Caller example and shape

A realistic usage example, the supporting types and signatures, and the flow of
data and errors. Explain what complexity the interface hides and what callers
still need to know.

## Decision and tradeoffs

The selected shape, why it meets the constraints, and the costs accepted.
If alternatives were compared, describe their material differences and why the
chosen shape won. If artifacts were combined, identify what came from each.
Do not invent alternatives or a synthesis that did not happen.

## Risks and verification

Unresolved assumptions, checks that could invalidate the design, and how the
implementation will be verified. Distinguish questions requiring user input from
routine decisions the owner can resolve.

## Next step

The next implementation unit, or the design-only handoff when implementation is
outside this task.
